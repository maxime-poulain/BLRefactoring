# 0008 — Regenerate the HTTP client from the API, and commit it automatically

- **Status:** Accepted
- **Date:** 2026-08-01

## Context

`src/TrainingHub.GeneratedClients/Clients.Generated.cs` — 1 956 lines, stamped NSwag 14.6.3 —
described an API that had stopped existing. It published `TrainingDto`, `TrainerDto`, `Error` and
`ErrorCode`: the application DTOs and the kernel's smart enum, everything ADR-less PR #43 removed
from the HTTP boundary in favour of `*RequestHttp` / `*ResponseHttp`. It knew nothing of
`/Trainer/me`, of `/Training/by-topic`, of paging or of `ProblemDetails`. Thirteen Blazor files
consumed it, and it compiled the entire time.

Worse, it was unreproducible. `generator.nswag` could not have produced it: its document generator
held a **JSON document pasted inline**, titled `"My Title"`, listing endpoints the client does not
have and missing ones it does. Its `runtime` said `Net80` on a net10.0 solution, and its fallback
URL pointed at `/swagger/v1/swagger.json` — a route ADR 0006 removed. The MSBuild target that would
have run it was commented out, named a `nswag.json` that does not exist, and invoked
`$(NSwagExe_Net10)`, a property that has never existed either; the real one is `NSwagExe_Net100`.

The real configuration lived in an NSwag Studio session that was never saved. That is the failure
mode of a GUI generator: it does not produce bad code, it produces code nobody can reproduce.

## Decision

**The client is generated by the NSwag CLI, from a script, and CI regenerates and commits it
whenever the API has changed.**

- **A CLI, not an MSBuild target.** An ordinary `dotnet build` regenerates nothing, so nobody pays
  for generation on every compile and no build scenario is complicated by it. Generation happens
  when someone decides — a script, before a pull request, in a pipeline.
- **`scripts/generate-clients.sh` is the single entry point**, run identically on a developer
  machine and in CI. One way to do it means one way for it to be wrong.
- **The CLI version is pinned** in `.config/dotnet-tools.json`. Without that, output changes when no
  code changed, and the CI check below turns into noise.
- **The document is emitted by the build**, by `Microsoft.Extensions.ApiDescription.Server` on the
  layered host, and the generator reads that file. It replaces loading the host assembly, which is
  what rotted before: an assembly path and a runtime moniker both go stale on every
  target-framework change, silently.
- **The generated file stays committed.** A consumer never has to run the generator, and the client
  can be read in the repository — which matters in a project whose purpose is to be read.
- **CI regenerates and commits.** This is the part that matters, and it is a stronger position
  than failing on difference: the API is the source of truth, so when a controller changes the
  client follows in the same push, without anyone being asked and without a red build to nag them
  into it. Nothing can be stale, because nothing waits for a human.
- **On pull requests too, which took a second attempt.** The first form of this workflow committed
  on `push` and *failed* on `pull_request`, on the reasoning that "the branch's own push has already
  regenerated". It has not: the two events fire together on the same commit, so the pull-request run
  is checked out before the push run's commit exists, finds the same difference, and fails on it.
  The bot's commit is made with `GITHUB_TOKEN`, which triggers no workflow — the same property that
  stops this looping is what stops the corrected tree from ever being re-checked — so the pull
  request stayed red until a human pushed something unrelated. Every API change cost one red check
  and one confused reader. The pull-request run now checks out the head branch rather than the merge
  commit and commits like the push run does. Only a fork, where the token cannot write, still turns
  the difference into a failure.
- **Consumers are expected to keep up, and breaking them is accepted.** A regenerated client can
  rename a type or a method, and whatever calls it stops compiling. That is the consumer's problem
  by design: the alternative is an API held back by its clients, which is how the old client came
  to describe endpoints that no longer existed.
- **Regeneration runs before the build**, so the same run compiles the solution against the client
  the API now implies — including whatever the regeneration just broke. Running it afterwards would
  report a green build for a client nobody had compiled yet.

The document comes from the **layered host** — the one the Blazor front end already calls, on
`:7249` — whose list endpoints return plain arrays. Generating from the CQRS host would return pages
and force a front-end migration for no gain.

## Consequences

- The client can be reproduced by anyone, on any machine, in one command.
- Drift cannot occur at all on the push path: the client is rewritten by the same event that
  changed the API. The specific defect that prompted this — a client that compiles and lies —
  becomes unrepresentable rather than merely detected.
- Changing an HTTP contract costs nothing to the person changing it. The cost lands on consumers,
  which is where this repository has decided it belongs.
- `NSwag.MSBuild` leaves the solution; nothing in the build knows about client generation any more.

Against that:

- **A build can go red for reasons nobody chose.** The regenerated client is committed whether or
  not the front end still compiles against it, so a controller change can leave the repository's own
  build broken until someone fixes the consumer. Accepted deliberately: the alternative is a
  published API that waits for its clients.
- **CI writes to the repository.** The workflow holds `contents: write` for that one step, and the
  history gains commits nobody typed. A push made with `GITHUB_TOKEN` does not trigger another
  workflow run, so it cannot loop.
- **A pull-request run no longer builds the merge.** Checking out the head branch is what lets the
  regeneration commit somewhere, and the cost is that the pull-request check now validates the same
  tree the push check does rather than its merge with `master`. Accepted for a repository whose
  branches are short-lived and whose base moves rarely; the merge is still validated when the branch
  is merged, by the push run on `master`. Reversing it means reverting to a red check on every API
  change, which is the state this replaced.
- **Two runs on one branch cannot race any more.** A `concurrency` group queues push runs rather
  than cancelling them, because they commit: two runs regenerating and pushing at once left the
  loser failing on a non-fast-forward nobody caused.
- **Renaming a C# action method is now a breaking change for clients.** `operationId` is
  `Controller_Action`, so `CreateTrainingAsync` publishes `Training_CreateTraining` and generates
  `TrainingClient.CreateTrainingAsync`. Renaming the method renames the published operation and the
  generated call — a refactor that used to be internal is now visible on the wire, and with
  automatic commits it ships without anyone reviewing the decision.
- **Generating loads the host.** Everything above `app.Run()` executes, including
  `EnsureDatabasesAreUpToDateAsync`, so a generation would migrate whatever database the
  configuration points at. `OpenApiDocumentGeneration.IsInProgress()` turns off that one call.
  It reads two signals: `OPENAPI_GENERATION`, which the script exports, and the entry assembly
  name, which contains `getdocument` when the document tool is what loaded the application — the
  tool is `dotnet-getdocument`, a name taken from a build log after the first guess at it was
  wrong. The second signal is the one that does not depend on remembering: a build started from an
  IDE with `-p:OpenApiGenerateDocuments=true` sets no variable.
  Note which process is detected: **NSwag never loads the host**, it reads a file. Looking for
  NSwag would find nothing.
- The CI job gets slower by a build and a generator run.

## Alternatives considered

**Failing the build on drift instead of committing.** The first form of this decision, and it
survived one afternoon. It puts the work on whoever changed the controller and turns every contract
change into a red build followed by a manual regeneration — pressure to keep the client current,
paid by the wrong person. Committing automatically says the same thing without the ceremony.

**MSBuild integration, generating on every build.** Guarantees the client is never stale, at the
price the user of this repository named: longer compiles for everyone, and awkward development
scenarios. `Microsoft.Extensions.ApiDescription.Client` would take it further and generate into
`obj/` with nothing committed, which makes drift structurally impossible rather than merely
detected. Rejected because the client would then be unreadable in the repository, and being read is
part of this project's job. The trade was made deliberately, and the CI check is what pays for it.

**NSwag Studio.** How the current state came about. A Windows GUI whose configuration lives outside
the repository, so what shipped could not be reproduced from what was committed. Fine for
exploring, never in a chain.

**Kiota.** Microsoft's newer generator, and the better answer for a large or third-party API: leaner
models, a maintained team behind it. Rejected here for a small, internal, .NET-to-.NET API: its
fluent path-segment API is harder to wrap and to mock, it adds runtime dependencies, and NSwag is
what the ASP.NET Core SDK's own client tooling uses.

**Refit.** The nicest calling code of any option, because the interface is written in the
consumer's own vocabulary — a genuine anti-corruption boundary rather than a generated approximation
of one. Rejected because that interface is maintained by hand, so drift becomes possible again,
which is the defect being fixed. `Refitter` closes that gap by generating the interfaces, at which
point the comparison is with NSwag on generator quality rather than on approach.

**A hand-written client.** Entirely defensible at this size — three controllers. Rejected for the
same reason as Refit: nothing but discipline keeps it aligned, and discipline is what failed.

**Sharing the contract types instead of generating.** Moving `*RequestHttp` / `*ResponseHttp` into a
project the front end also references would make drift impossible by construction, since both sides
would compile against the same types. Legitimate only because both ship together; it would be wrong
the moment a third party consumed this API, and it would remove the demonstration of contract-first
client generation that the repository exists to show.
